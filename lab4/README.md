# Лабораторная работа 4. Spring Security: аутентификация и авторизация (вариант 9)

REST-сервис для планирования музейных выставок. Музей хранит **экспонаты**, располагает **экспозиционными залами**
и проводит **выставки** под руководством **кураторов**. Экспонаты **размещаются** на выставках в конкретных залах.
Сервис следит, чтобы залы не были переполнены, выставки открывались только подготовленными, а данные оставались
согласованными при любых изменениях.

Продолжение лабораторной работы 3: к API добавлены учётные записи, регистрация, HTTP Basic, CSRF-защита и
разграничение доступа по ролям и по контексту операции.

Стек: Java 21, Spring Boot 4.0.9, Spring Security 7, Spring Data JPA, Flyway, PostgreSQL 17 (Docker), Maven.

## Безопасность

### Аутентификация
- **HTTP Basic**: логин и пароль передаются в каждом запросе, сессии не создаются.
- Учётные записи хранятся в таблице `users`; пароли — только в виде хеша **BCrypt** (стоимость 12).
- **Регистрация** `POST /api/auth/register` доступна без входа. Новый пользователь всегда получает роль `VISITOR`;
  поле `role` в запросе игнорируется, повысить роль может только администратор.
- **Политика паролей**: не короче 12 символов и не длиннее 72 байт (ограничение BCrypt), заглавные и строчные
  буквы, цифра, спецсимвол, без пробелов, без распространённых паролей, логина и email. Логин и email уникальны
  (без учёта регистра).
- **Состояния учётной записи**:
  - `ACTIVE` — вход разрешён; `BLOCKED` — заблокирован администратором, вход запрещён;
  - временная блокировка: после 5 неверных паролей подряд вход запрещён на 15 минут (даже с верным паролем);
    успешный вход сбрасывает счётчик, администратор может снять блокировку досрочно (`PATCH {"status": "ACTIVE"}`);
  - пользователь без пароля (демо-кураторы из тестовых данных) войти не может.
- Первый администратор создаётся при запуске из `ADMIN_USERNAME`/`ADMIN_EMAIL`/`ADMIN_PASSWORD` (файл `.env`),
  если в БД ещё нет администратора. Пароли в репозитории не хранятся.

### CSRF
- Используется схема double submit cookie: `GET /api/auth/csrf` возвращает `{"headerName": "X-XSRF-TOKEN", "token": "..."}`
  и устанавливает cookie `XSRF-TOKEN` (`SameSite=Strict`).
- Все запросы, изменяющие данные (`POST`, `PATCH`, `DELETE`), включая регистрацию и бизнес-операции, должны передавать
  cookie и заголовок `X-XSRF-TOKEN` с тем же значением.
- Токен не сбрасывается при каждой Basic-аутентификации (иначе он становился бы недействительным после первого же
  запроса), так как сессий нет и фиксировать нечего.

### Роли и права
| Право | ADMIN | CURATOR | VISITOR |
|---|:-:|:-:|:-:|
| Просмотр выставок, экспонатов, залов, размещений | ✓ | ✓ | ✓ |
| `USER_MANAGE` — управление пользователями и ролями (`/api/users`) | ✓ | | |
| `HALL_MANAGE` — создание, изменение, удаление залов | ✓ | | |
| `EXHIBIT_MANAGE` — создание и изменение экспонатов, отправка на реставрацию | ✓ | ✓ | |
| `EXHIBIT_DELETE` — удаление экспонатов | ✓ | | |
| `EXHIBITION_CREATE` — создание выставок (куратором назначается сам автор) | ✓ | ✓ | |
| `EXHIBITION_MANAGE_ANY` — изменение, открытие, закрытие, отмена, удаление любых выставок и их размещений | ✓ | | |

**Контекстные правила** (`@PreAuthorize` + бин `AccessPolicy`):
- куратор изменяет, открывает, закрывает и отменяет **только выставки, где он назначен куратором**, и управляет
  размещениями (создание, PATCH, монтаж, перенос, удаление) только на своих выставках;
- куратор не может назначить куратором выставки другого пользователя;
- удалять выставки может только администратор.

**Согласование с бизнес-логикой** (нарушение — `409`):
- куратором выставки может быть только активный пользователь с ролью `CURATOR`;
- нельзя заблокировать или удалить куратора открытой выставки и понизить роль куратора незавершённых выставок;
- администратор не может изменить свои роль и статус или удалить себя;
- права не отменяют бизнес-ограничений: даже администратор не удалит открытую выставку.

Доступ настроен в два уровня: `SecurityFilterChain` (публичные `/api/auth/csrf` и `/api/auth/register`,
`/api/users/**` только с `USER_MANAGE`, остальной `/api/**` только после входа, прочие пути запрещены) и
`@PreAuthorize` на каждом методе контроллеров, изменяющем данные.

### Ошибки
| Код | Когда | `code` в ответе |
|---|---|---|
| `401` | нет учётных данных, неверный пароль, учётная запись заблокирована или не существует | `AUTHENTICATION_REQUIRED` |
| `403` | нет или неверный CSRF-токен | `CSRF_TOKEN_INVALID` |
| `403` | недостаточно прав (роль или контекст) | `ACCESS_DENIED` |
| `400` / `404` / `409` | ошибка запроса / объект не найден / нарушение бизнес-ограничения | — |

Ответ `401` одинаков для любых причин, поэтому по нему нельзя узнать, существует ли пользователь или заблокирован ли он.
Ответы не содержат стектрейсов, SQL и внутренних сообщений исключений; непредвиденные ошибки — общий `500`
(подробности только в логе сервера). Пароли и хеши никогда не возвращаются в ответах.

## Предметная модель

```
users 1 ──── 0..* exhibitions          (куратор выставки)
exhibits 1 ── 0..* exhibit_placements ── 0..* 1 exhibitions
exhibition_halls 1 ──── 0..* exhibit_placements
```

| Сущность | URL | Поля | Описание |
|---|---|---|---|
| Пользователь | `/api/users` | `username`, `fullName`, `email`, `role`, `status`, `lockedUntil` | Учётная запись: администратор, куратор или посетитель |
| Экспонат | `/api/exhibits` | `name`, `condition`, `requiredArea` | Предмет коллекции и площадь (м²), нужная для экспонирования |
| Экспозиционный зал | `/api/exhibition-halls` | `name`, `area`, `available` | Зал с площадью (м²); недоступный зал (ремонт) нельзя занимать |
| Выставка | `/api/exhibitions` | `title`, `startDate`, `endDate`, `status`, `curatorId`, `openedAt`, `closedAt` | Период проведения и жизненный цикл |
| Размещение экспоната | `/api/exhibit-placements` | `exhibitId`, `exhibitionId`, `hallId`, `mountingStatus`, `mountedAt` | Какой экспонат, на какой выставке, в каком зале и в каком состоянии монтажа |

Перечисления:
- состояние экспоната `condition`: `EXCELLENT`, `GOOD`, `SATISFACTORY`, `NEEDS_RESTORATION`;
- статус выставки `status`: `PLANNED` → `ACTIVE` → `COMPLETED`, либо `PLANNED` → `CANCELLED`;
- статус монтажа `mountingStatus`: `PLANNED`, `IN_PROGRESS`, `MOUNTED`, `DISMANTLED`.

Поля `id`, `createdAt`, `updatedAt`, `openedAt`, `closedAt`, `mountedAt` и статусы задаёт сервер; значения из запроса игнорируются.

## Бизнес-операции

| # | Операция | Запрос | Затрагивает | Когда допустима | Результат |
|---|---|---|---|---|---|
| 1 | Смонтировать экспонат | `POST /api/exhibit-placements/{id}/mount` | размещение, экспонат, зал, выставка | размещение `PLANNED`/`IN_PROGRESS`; выставка не завершена и не отменена; зал доступен; экспонат не требует реставрации | `MOUNTED`, `mountedAt` = сейчас |
| 2 | Перенести экспонат в другой зал | `POST /api/exhibit-placements/{id}/move` `{"hallId": N}` | размещение, залы, выставка | размещение не демонтировано; экспонат не выставлен на открытой выставке; целевой зал другой, доступен и вмещает экспонат на период выставки | зал изменён, монтаж сброшен в `PLANNED` |
| 3 | Открыть выставку | `POST /api/exhibitions/{id}/open` | выставка, размещения, куратор | статус `PLANNED`; назначен куратор; сегодня в периоде проведения; есть хотя бы один экспонат и все смонтированы | `ACTIVE`, `openedAt` = сейчас |
| 4 | Закрыть выставку | `POST /api/exhibitions/{id}/close` | выставка, размещения | статус `ACTIVE` | `COMPLETED`, все размещения `DISMANTLED`, при досрочном закрытии `endDate` = сегодня |
| 5 | Отправить экспонат на реставрацию | `POST /api/exhibits/{id}/send-to-restoration` | экспонат, размещения | экспонат ещё не ждёт реставрации и не выставлен на открытой выставке | `NEEDS_RESTORATION`, его размещения на незавершённых выставках демонтируются (освобождают залы) |
| 6 | Отменить выставку | `POST /api/exhibitions/{id}/cancel` | выставка, размещения | статус `PLANNED` | `CANCELLED`, размещения `DISMANTLED` |

### Правила вместимости залов
Зал одновременно используют все незавершённые выставки, периоды которых пересекаются. Суммарная `requiredArea`
недемонтированных экспонатов таких выставок не может превышать `area` зала. Правило проверяется при создании и
изменении размещения, переносе, изменении площади экспоната, изменении дат выставки и уменьшении площади зала.

### Ограничения CRUD-операций
- Статусы выставок меняются только бизнес-операциями; через `PATCH` размещения доступны лишь `PLANNED` и `IN_PROGRESS`.
- Даты меняются только у запланированной выставки; завершённые и отменённые выставки не редактируются.
- Нельзя удалить открытую выставку, а также зал, экспонат или размещение, задействованные в открытой выставке.
- Нельзя удалить пользователя, который курирует открытую выставку; в остальных случаях он снимается с роли куратора.
- Нельзя сделать зал недоступным, пока в нём идёт открытая выставка.

### Целостность и корректность
- Каждая операция выполняется в одной транзакции: при отказе изменения не сохраняются.
- Строка зала блокируется (`SELECT ... FOR UPDATE`) на время проверки вместимости, поэтому параллельные запросы не переполнят зал.
- У всех сущностей есть поле `version` (оптимистическая блокировка); одновременное изменение одной записи возвращает `409`.
- На уровне БД: внешние ключи (`ON DELETE CASCADE` для размещений, `ON DELETE SET NULL` для куратора), `UNIQUE`
  (логин, email, название зала, экспонат на выставке не более одного раза), `CHECK` (площади > 0,
  `end_date >= start_date`, допустимые статусы, у открытой выставки задан `opened_at`, у смонтированного экспоната — `mounted_at`).

## Ответы API
`200` — чтение, обновление, бизнес-операция; `201` — создание (JSON с `id`); `204` — удаление;
ошибки — см. раздел «Ошибки», формат `application/problem+json`.

Дополнительные эндпоинты: `GET /api/auth/csrf`, `POST /api/auth/register`, `GET /api/auth/me` (профиль текущего пользователя).

## База данных и роли
| Роль | Права | Назначение |
|---|---|---|
| суперпользователь `postgres` | все | только первичная инициализация контейнера |
| `museum_owner` | владелец БД и схемы | выполняет миграции Flyway |
| `museum_app` | `SELECT/INSERT/UPDATE/DELETE` на таблицы предметной области | все запросы приложения; не может менять схему, `TRUNCATE`, создавать роли и читать историю миграций |

Роли создаёт `docker/postgres/init/01-create-roles.sh`. Схема — `src/main/resources/db/migration`,
тестовые записи — `db/seed`, отзыв прав на служебную таблицу Flyway — `db/postgres/afterMigrate.sql`.
Учётные записи — миграция `V2__user_accounts.sql` (хеш пароля, роль, статус, счётчик неудачных входов;
`CHECK` на формат хеша BCrypt). Пароли хранятся только в `.env` (не коммитится), шаблон — `.env.example`.

## Запуск
```bash
cp .env.example .env        # задайте свои пароли, в том числе ADMIN_PASSWORD
docker compose up -d        # PostgreSQL 17 + роли
./mvnw spring-boot:run      # миграции и тестовые данные применятся автоматически
```
Тесты (`./mvnw test`) используют H2 в режиме PostgreSQL и не требуют Docker: бизнес-операции (`MuseumApiTests`)
и безопасность (`SecurityTests`: CSRF, регистрация, 401/403, роли, контекст куратора, блокировки).

## Коллекция запросов
`postman/museum.postman_collection.json` — импортируйте в Postman, задайте переменные `adminUser`/`adminPassword`
(значения `ADMIN_USERNAME`/`ADMIN_PASSWORD` из `.env`) и запустите через Collection Runner (102 запроса).

Скрипт коллекции автоматически подставляет CSRF-токен в заголовок `X-XSRF-TOKEN` для изменяющих запросов,
а авторизация задана на уровне папок (у отдельных запросов — свой пользователь):

0. получение CSRF-токена, регистрация (без токена — 403, со слабым паролем — 400, повтор — 409, попытка стать ADMIN игнорируется), 401;
1. посетитель: просмотр разрешён, изменения и список пользователей — 403;
2. администратор: создание кураторов, залы, запрет на понижение собственной роли;
3. куратор: экспонаты, свои выставки и размещения, попытка назначить чужого куратора — 403;
4. второй куратор: чужая выставка — только просмотр, изменения — 403;
5. бизнес-операции из ЛР3 с проверкой ролей и бизнес-ограничений (403 и 409 различаются);
6. временная блокировка после 5 неверных паролей, разблокировка и блокировка администратором;
7. удаление администратором с проверкой ссылок.

Даты и имена пользователей уникальны для каждого прогона, коллекцию можно запускать повторно.
